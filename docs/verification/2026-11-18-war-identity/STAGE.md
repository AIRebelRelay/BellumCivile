## Root cause, callers and blast radius

WarKey is an unordered pair; StartedDay is float. New recorded wars can share both,
so those values cannot uniquely identify a stored conflict instance. There are two
production allocations: WarScoreBehavior.RegisterConflict and the custom Bellum
WarScoreAiInfluenceForeignLedger registration path. Both use the single existing
constructor. Ordinary RegisterConflict first reuses an existing ACTIVE pair record;
otherwise it constructs a new one. Legacy ledger admission preserves its existing
event/context idempotency and rejection rules. Neither allocator is edited.

Existing records can be continued/retargeted by TryRetargetCivilWarDefender and
TryPromoteRivalry. Those functions must retain the record ID while preserving their
participant/context/score-perspective behavior. The ID is NOT an assertion that
all those participants/context/rulers remain unchanged.

The only live lifecycle hook changed is WarScoreBehavior.SyncData, already used to
load/save the existing war list and recover raid history. No reader/list guard gains
lazy allocation; no event scheduler or action owner changes.

## Exact production change

WarScoreRecord.cs appends [SaveableField(38)] private string _conflictInstanceId.
All original37 declarations across WarScoreRecord.cs, WarScorePeaceReconsideration.cs
and WarScoreFeudObjective.cs retain their exact IDs/types/names. Save typeID31,
save key BellumCivile_WarScore_Wars, class hierarchy and constructor signature stay.

The constructor calls InitializeMissingConflictInstanceId once. That helper only
allocates for NULL using Guid.NewGuid().ToString("N"). Existing valid or malformed
non-null evidence is never overwritten. ConflictInstanceId is a passive read-only
canonical-valid/nonempty GUID projection; missing or malformed evidence returns null.

SyncData retains original SyncData -> list guard -> raid-history recovery order and
adds null-only identity initialization AFTER raid-history recovery for each record.
It does not change score/events/active or pending flags, timestamps, context, pairs,
revisions, treaty state or political effects. No GUID is generated by a getter.
Metadata1.4.12.8, build example identity and cumulative suite entry are updated;
builder/Naval behavior and logger/package fixture are unchanged.

## Legacy and identity limits

Legacy load without field38 assigns an ID in memory. The NEXT upgraded save persists
that allocation. Repeatedly loading an unchanged original PRE-upgrade save can assign
a different ID because it contains no previous allocation; do not claim continuity
until the upgraded state is actually saved. A first in-memory null-only repair during
saving is not independently claimed persisted by that same SyncData call: the normal
upgrade path is load migration, then a subsequent save with an existing ID.

IDs identify RECORDED-CONFLICT lifetime, not independently verified every engine war
incarnation. If an earlier missed peace/reconciliation event leaves an old record
active and existing registration reuses it, this patch deliberately does not guess
that a new engine war occurred. Future authoritative binding must reconcile the
actual game stance/incarnation as well as this ID. Pair/time alone remains insufficient.
Corrupt duplicated non-null GUIDs are not silently rewritten; a future unique-match
resolver must reject ambiguous tracked records. Do not treat a valid GUID alone as
proof of world identity, execution authority, actor consent or an outcome receipt.

Existing public snapshot DTOs/Bridge contracts are NOT extended here. No timer,
request, consent, journal operation, treaty or news consumes this ID yet. New GUIDs
for internal/legacy-ledger records do not transfer their domain ownership.
